# 성능 개선 적용 및 프로젝트 점검

점검일: 2026-09-18. 현재 로컬 소스와 한국대학교 데이터 기준.

## 이번에 적용한 개선

| 작업 | 변경 내용 | 검증 결과 |
|---|---|---|
| PDF 병합 | 웹 서버와 분리된 작업 스레드에서 병합. 별도 스레드 안에서 PDF 파싱·저장 시 불필요한 대기 제거. 동시 병합은 1개로 제한해 메모리 사용량 통제 | 기존 생성 PDF 40개·197쪽: 23,112ms → 1,066ms |
| 병합·ZIP 대상 조회 | 정렬에 필요한 조건, 생성 단위, 분할 순서만 조회. 양식 전체 내용 제외. 파일 존재 확인은 최대 16개 동시 실행 | 200건 조회 데이터: 19,994,472 → 279,472바이트. 정렬 결과 동일 |
| 사진 일괄 등록 | 파일 저장 4개 동시 처리, DB 갱신 최대 200행씩 묶음. 같은 사진을 사용하는 여러 수험생 행 연결 유지. 처리 실패 시 진행 중 저장이 끝난 후 DB 롤백 | 테스트용 사진 1,000장: 1,079ms → 393ms. DB 갱신 1,000회 → 5회 |
| PDF용 사진 읽기 | 한꺼번에 모든 사진을 읽던 방식을 최대 8개 동시 읽기로 제한 | 기존 사진 포함·누락 동작 테스트 통과 |
| 병합·ZIP 결과 목록 | 파일 상태 확인을 최대 16개 동시 처리. 목록 순서 유지 | 결과 목록 테스트 통과 |

### 측정 범위와 한계

- 로컬에서 측정한 대표 실행 결과이며, 운영 서버·인터넷 업로드/다운로드 시간은 포함하지 않는다.
- PDF 병합은 실제 기존 생성 파일을 읽었고, 원본을 변경하지 않았다. 결과 총 197쪽을 확인하고 1·99·197쪽을 렌더링해 전후 PNG 파일 해시가 모두 같음을 확인했다.
- 사진 측정은 32KB짜리 테스트 파일 1,000개와 현재 DB의 임시 테이블을 사용했다. 실제 수험생 행과 사진은 변경하지 않았다. 이 수치는 사진 저장 단계이며 ZIP 전송·전체 압축 해제 시간은 포함하지 않는다.
- 병합 중 웹 서버 이벤트 루프의 최대 지연은 같은 측정에서 128ms → 15ms였다. 이 값은 대표 실행의 관찰값이며 부하 환경에 따라 달라진다.
- 전체 자동 테스트 555개 통과. 병합 실패 후 다음 작업 처리, 페이지 순서, 사진 다중 행 매핑, 제한된 동시 실행, 실패 시 롤백도 검증했다.

### 확인한 사항

- 자동 테스트 566개 통과 및 클라이언트 빌드 완료. 브라우저에서 목록 페이지 이동·필터·작업 로그·PDF 양식 선택을 확인했다.
- 편집기 계측 결과는 개발자 콘솔의 `getExamListPerformanceMetrics()`에서 확인할 수 있다. 문서 내용은 기록하지 않고 횟수·시간만 메모리에 유지한다.
- DB 변환 전 요청 기록은 로컬 진단 폴더에 백업했고, 실제 수험생/양식 내용은 바꾸지 않았다. 검증용 병합 결과와 작업 기록은 검증 후 정리했다.
- 테스트 수치는 로컬의 대표 실행 결과다. 운영 서버, Cloudflare 경유 전송 시간, 실제 네트워크 업로드 속도는 별도 환경에서 확인해야 한다.

### 서버 업데이트 시 동작

1. 서버와 별도 PDF 작업 프로세스를 중지하고 소스를 업데이트한다.
2. 기존 시작 절차로 재기동한다. 새 테이블과 과거 PDF 요청 변환은 첫 실행에서 자동 적용된다. 최초 변환은 데이터 양에 따라 시간이 추가될 수 있다.
3. 이후 재기동은 적용된 DB 변경을 건너뛴다. 브라우저를 새로고침하면 새 화면 코드가 적용된다.

업로드·병합 도중 브라우저의 일시적인 조회 연결이 끊기면 동일 작업 ID로 다시 조회한다. 서버 자체가 재시작되어 중단된 작업은 실패 상태로 표시하며, 데이터를 중복 반영하지 않도록 자동 재실행하지 않는다. 이 경우 반영 결과를 확인한 뒤 다시 실행한다.
